## 三、安全问题

### 3.1 🔴 `assetProtocol` scope 放行整个文件系统

**位置**:`packages/@codepapr/ui/src-tauri/tauri.conf.json:27`

```json
"assetProtocol": { "enable": true, "scope": ["$HOME/**", "/**", "C:/**", "D:/**", "E:/**", "F:/**"] }
```

asset 协议允许 webview 通过 `convertFileSrc` 读取**磁盘上任意文件**。配合 CSP 中 `img-src 'self' asset: ... https: data:`,一旦渲染层存在注入点(例如 markdown/网页内容中构造 `<img src="asset://localhost/$HOME/.ssh/id_rsa">`),攻击者可探测文件存在性,甚至配合外发通道(`https:` 连接是放行的)做内容外泄。

当前前端只在已知工作区路径上调用 `convertFileSrc`(`chatImageStore.ts:55`、`CodePreviewPanel.tsx:430`),但这是**前端自律而非边界强制**。对一个会渲染 LLM 生成内容和抓取网页的应用,这条信任边界应当收紧。

**建议**:
- scope 收缩为"当前工作区 + 应用数据目录(聊天图片)"。Tauri 支持在运行时按工作区切换动态 `asset_protocol_scope()` 增删 scope,切换项目时同步调整。
- 或改用自定义 `codepapr-app://` 协议(项目已有 `register_uri_scheme_protocol`),在 Rust 侧强制校验路径归属。

### 3.2 🔴 `http` 插件 capability 放行任意 URL

**位置**:`packages/@codepapr/ui/src-tauri/capabilities/default.json`

```json
{ "identifier": "http:default",
  "allow": [{ "url": "https://**" }, { "url": "http://**" }, { "url": "http://localhost:**" }] }
```

Rust 侧的 `fetch_web_url` / `download_web_file` 有完整的 SSRF 防护(`web/client.rs:37` `ssrf_safe_blocking_get`:逐跳内网校验 + DNS pin + 手动重定向跟随),但 `tauri-plugin-http` 的 JS 命令(`@tauri-apps/plugin-http` 的 fetch)**不经过这些防护**——前端代码可以直接请求 `http://169.254.169.254`(云元数据)、`127.0.0.1` 上的任意本地服务。

**建议**:
- 若前端确实需要直连本地预览端口,只保留 `http://localhost:**` 与 `http://127.0.0.1:**`,删除 `https://**` / `http://**`;所有外网请求统一走 Rust 命令。
- 或完全移除 `tauri_plugin_http`,网络能力全部收口到 Rust。

### 3.3 🟠 `export_text_file` 无路径校验

**位置**:`packages/@codepapr/ui/src-tauri/src/file_export.rs:6`

```rust
pub fn export_text_file(save_path: String, content: String) -> Result<(), String> {
    std::fs::write(&save_path, content.as_bytes()).map_err(|e| e.to_string())
}
```

注释声称"路径由系统保存对话框挑选",但 IPC 契约并不强制这一点——webview 侧任何能发起 `invoke('export_text_file')` 的代码路径(包括被注入的渲染内容)都可以覆盖任意当前用户可写的文件(如 `~/.zshrc`)。

**建议**:在 Rust 侧校验:要求 `save_path` 的父目录属于用户目录白名单(桌面/文档/下载/工作区),或要求前端先通过 `dialog` 命令拿到带标记的路径再校验。同类命令 `character_card::save_character_avatar` 也建议一并核查。

### 3.4 🟠 `stronghold:default` capability 暴露未使用的命令面

**位置**:`capabilities/default.json` + `main.rs:149-157`

项目实际用自己管理的 Stronghold 实例(`vault.rs`),`tauri_plugin_stronghold` 的注册用的是占位 hash 函数(注释明确"never invoked")。但 `stronghold:default` 权限仍把插件的 JS 命令(加载任意 snapshot 文件等)暴露给了前端。

**建议**:从 capabilities 移除 `stronghold:default`;若插件 JS API 完全不用,评估直接移除插件注册(或保留插件仅用其依赖)。

### 3.5 🟡 MCP SSE 无界通道

**位置**:`src-tauri/src/mcp_sse.rs:78-80`

```rust
let (outgoing_tx, mut outgoing_rx) = mpsc::unbounded_channel::<ClientJsonRpcMessage>();
let (incoming_tx, incoming_rx) = mpsc::unbounded_channel::<ServerJsonRpcMessage>();
```

恶意或故障的 MCP 服务器高速推送消息时内存会无界增长。建议改为 `mpsc::channel(bounded)` 并在满载时断开该服务器连接。另外 `mcp_host.rs` 的结果已有 `result_max_bytes` 上限(默认 200KB),这点做得对。

### 3.6 值得肯定的安全设计(保持)

- **命令执行沙箱**:`shell/sandbox.rs` 用 macOS SBPL 限制工作区写、网络、`.CodePapr` 内部目录,并正确处理了 `/var/folders` 符号链接规范化。
- **密钥存储**:`vault.rs` 已修复 lossy-UTF8 口令熵坍缩问题(有迁移路径与回归测试),`vault.key` 以 0600 原子创建。
- **路径遍历**:`shared/paths.rs` 拒绝 `..`、绝对路径与根前缀,`canonicalize` 后再做可达性校验。
- **SQL**:全部参数化(`db/mod.rs`),FTS MATCH 查询对 token 做了引号包裹与 `"` 剥离(`db/mod.rs:3938-3944`)。

## 四、Bug 与正确性

### 4.1 🔴 窗口关闭:清理在主线程同步执行 + 执行两次

**位置**:`src-tauri/src/main.rs:469-500`

```rust
.on_window_event(|window, event| {
    if matches!(event, tauri::WindowEvent::CloseRequested { .. }) {
        if window.app_handle().windows().len() <= 1 {
            let _ = window.emit("codepapr:flush-settings", ());
            let epoch_before = db::settings_save_epoch();
            db::wait_for_settings_save_epoch(epoch_before, Duration::from_millis(2000));
            window.app_handle().exit(0);
        }
        run_shutdown_cleanup();      // ← ① 主线程同步执行
    }
})
// ...
.run(|_handle, event| {
    if matches!(event, tauri::RunEvent::Exit) {
        std::thread::spawn(run_shutdown_cleanup);  // ← ② 再来一次
    }
});
```

三个问题叠加:

1. **主线程阻塞**:`run_shutdown_cleanup()` 在 `CloseRequested` 回调里**同步**执行,而紧随其后的 `RunEvent::Exit` 分支的注释自己写道:"清理必须在独立线程执行……CDP close 可达 120s/页、child.wait 无限等待,进程会永远残留"。`CloseRequested` 这条路径恰恰犯了这个错——关窗时可能卡住数秒到两分钟(关窗 → 无响应 → macOS 彩虹圈)。
2. **重复执行**:①与②必然先后都跑(①执行完事件循环才走到 Exit),`stop_all_servers`/`disconnect_all` 等虽幂等,但浏览器页关闭这类副作用型清理跑两遍没有好处。
3. **无条件 2 秒等待**:即使没有任何待保存内容,`wait_for_epoch` 也会忙等满 2000ms(`db/mod.rs:1148-1157` 循环睡 10ms 直到超时),每次退出都白白卡 2 秒。

**建议**:
- `CloseRequested` 分支只做:emit flush → 有界等待(可先探测"是否有在途保存"再等)→ `exit(0)`;清理完全交给 `RunEvent::Exit` 的独立线程。
- `wait_for_epoch` 前加一个"自上次纪元以来是否发生过保存请求"的快速判断,无事可等立即返回。

### 4.2 🟠 代码分割失效(两处)

**位置**:vite 构建输出(`npm run build` 可见):

```
[INEFFECTIVE_DYNAMIC_IMPORT] src/store/internals/projectSnapshot.ts is dynamically imported by
  src/store/charactersStore.ts but also statically imported by src/store/agentStore.ts, ...
[INEFFECTIVE_DYNAMIC_IMPORT] src/store/agentStore.ts is dynamically imported by
  src/store/appRuntimeStore.ts, ... but also statically imported by src/App.tsx, ...
```

`agentStore.ts` 本意想懒加载(它拖着 861KB 的 chunk),但被 `App.tsx` 等多处**静态**导入,动态导入完全失效——首屏照样加载全部。`projectSnapshot.ts` 同理。

**建议**:二选一——要么接受现状把这些 `import()` 改成静态导入(消除误导),要么把 `App.tsx` 等入口对 `agentStore` 的依赖改为延迟获取(`useAgentStore.getState()` 模式配合真正的动态导入)。

**位置**:`npm run build` 输出

桌面应用从磁盘加载,首包不是生死线,但 `agentRuntime.worker` 每次创建/崩溃重建(心跳超时即重建,见 `WorkerBackedAgent.ts:107-122`)都要重新解析 6MB,直接拉长崩溃恢复时间。

### 4.4 🟡 退出 flush 只等"设置保存",不等角色卡

**位置**:`src/utils/settingsFlush.ts:17-31` + `main.rs:479-481`

`codepapr:flush-settings` 处理器先存设置、再 `flushCharactersState()`;Rust 侧只等待**设置保存纪元**推进(`wait_for_settings_save_epoch`)。若角色卡有脏数据,等待在设置落库后就返回,角色卡保存可能赶不上进程退出。

**建议**:为角色卡保存也建一个纪元(或把两类保存合并进同一纪元计数),退出时一起等。

### 4.5 🟡 两处 skip 的测试

**位置**:`npm test` 输出 `1643 passed | 2 skipped (1645)`

UI 包有 2 个被跳过的测试。建议确认后恢复或删除,避免长期"挂账"。

### 4.6 🔴 `selectSession` 图片回填竞态(静默丢消息)

**位置**:`src/store/agentStore.ts:1379-1389`

`selectSession` 的缓存分支用**选中时刻的快照** `cached` 调 `hydrateImageMessages(workspacePath, cached)`,异步回填图片后才 `set({ sessionMessages: { [id]: hydrated } })`。守卫只检查 `activeSessionId === id && workspacePath` 未变,**没有检查该会话的消息数组是否已被并发回合更新**。

触发场景:用户切回一个后台仍在流式输出的会话(`keepAgent` 分支保留 agent),回填完成时用过期快照整体覆盖 `sessionMessages[id]`,丢弃回填期间追加/更新的消息。

**修复**:写回前比较 `get().sessionMessages[id]` 是否仍是 `cached`(引用相等),或只把解析出的图片按消息 ID 合并进当前数组。

### 4.7 🔴 `turnInFlight` 置位与 `try` 之间存在可抛错窗口

**位置**:`src/store/internals/sendMessage.ts:914-936 / 1033`

`turnInFlight = true`(917 行)与 `try` 块(1033 行)之间有 `await get().ensureDefaultWorkspace()` 等约 100 行代码。目前 `ensureDefaultWorkspace` 内部吞错所以安全;但只要这段窗口内将来新增任何会抛错的代码,`finally` 就不会执行,`turnInFlight` 永久为真——**整个应用再也发不出消息**(所有发送在 914 行被静默拒绝)。

**修复**:把 `turnInFlight = true` 移到 `try` 块内第一行,或置位紧贴 `try` 且中间不允许任何 `await`。

### 4.8 🟠 `TtsInstaller` 监听器泄漏 + 吞错

**位置**:`src/components/TtsInstaller.tsx:60-70`

`startInstall` 直接 `unlistenRef.current = await listen(...)`,重复点击安装(或取消后重装)会覆盖旧引用而不调用旧 `unlisten`,监听器累积;且 `invoke('tts_install', ...).catch(() => {})` 完全吞掉安装启动失败,用户看不到任何错误反馈。

**修复**:赋值前先 `unlistenRef.current?.()`;invoke 失败时 `setRunning(false)` 并展示错误。

### 4.9 🟠 `ProjectGraphKnowledgeGraph` 异步 render 与 destroy 竞态

**位置**:`src/components/ProjectGraphKnowledgeGraph.tsx:1114-1124,1168-1174`

`graph.render()` 是异步的,而 cleanup 会 `graph.destroy()`。effect 依赖里有 `handleNodeClick`、`dark`、`focusKey` 等,若在 render 完成前重跑,`.then` 回调会对已销毁的图实例调用 `applyGraphHighlight`,抛错进入 `setGraphError`,造成误报"图渲染失败"。

## 五、性能(前端专项)

### 5.0 🟠 流式渲染的每帧全量派生计算

**位置**:`src/components/ChatPanel.tsx:205,284-300,600-621`

流式 delta 已做 240ms/4KB 双层合批(很好),但每次合批都会触发:`visibleMessages` 过滤、`sessionLock` 对全部消息的 `filter`、`messageHeights` 对**全部**可见消息重算、`prefixHeights` O(n) 前缀和。长会话(数千消息)下这些每 240ms 全量跑一遍。

### 5.0.1 🟠 worker 日志不同步即全量克隆

**位置**:`src/agent/WorkerBackedAgent.ts:686-688`

## 七、核心逻辑层(@codepapr/core、api、common、editor)

### 7.1 🔴 DeepSeekProvider 流内 `chunk.error` 未分类 → 无限重连死锁

**位置**:`packages/@codepapr/api/src/providers/DeepSeekProvider.ts:199-261`

OpenAIProvider(221-230 行)、ClaudeProvider(294-303 行)、ResponseProvider(442-450 行)都显式处理了流内 `chunk.error`,并用 `isRetriableStreamErrorType` 分类——注释里明确写了"旧实现忽略它……叠加无限重连永久卡死"。但 `DeepSeekProvider` 的 `streamChatCore` 完全没有 `chunk.error` 分支,`DeepSeekStreamChunk` 接口甚至没有声明 `error?` 字段。

后果链:中转以 SSE data 下发鉴权失败/欠费/上下文超限错误后干净关流 → `sawDone=false && sawFinishReason=false` → 抛 `retriable: true` 的 "Stream ended prematurely" → `withStreamIdleRetry` 默认 `maxRetries: undefined`(无限重试)→ 每 5~30 秒重连一次,**永久卡死并持续烧请求**,用户看到的只是"重试中"。

**修复**:给 `DeepSeekStreamChunk` 加 `error?: { message?: string; type?: string }`,在 chunk 处理循环中加入与 OpenAIProvider 相同的分类逻辑(`isPersistentStreamErrorType`/`isRetriableStreamErrorType`),并让 `ProviderRequestError` 原样穿透。

### 7.2 🔴 Claude 截断不触发续写守卫

**位置**:`providers/ClaudeProvider.ts:354、416、491、589` ↔ `agent/Agent.ts:1129`

Agent 的截断续写守卫只认 `choice.finishReason === 'length'`(Agent.ts:1129)。Anthropic 的输出耗尽信号是 `stop_reason: 'max_tokens'`,ClaudeProvider 流式(354 行)与非流式(589 行)都原样透传。于是 Claude 路线输出被 `max_tokens` 截断时,Agent 把它当正常完成:部分内容直接落日志、回合静默结束——这正是续写机制要防的 bug(Claude 开 thinking 时思考计入 `max_tokens`,截断概率更高)。对比:DeepSeek/OpenAI 路线有 `outputTokens >= maxTokens → 'length'` 的降级推断(如 OpenAIProvider.ts:311-316),Claude 路线两者皆无。

**修复**:在 ClaudeProvider 出口处把 `stop_reason === 'max_tokens'` 归一化为 `'length'`(流式与非流式两处),或在 Agent 侧同时接受 `'max_tokens'`。

### 7.3 🟠 ResponseProvider:截断放行 + `incomplete` 未映射

**位置**:`providers/ResponseProvider.ts:638-651、802`

- **流式**:OpenAI/DeepSeek 的规则是"没有 `[DONE]`/`finish_reason` 一律抛可重试错误"。ResponseProvider 的判定却是 `!sawDone && !sawFinishReason && !content && toolCallStates.length === 0`——只要已吐出**部分**内容就放行,且 651 行 fallback 为 `'stop'`。网关截断但已发半截文本时,部分内容以 `finishReason='stop'` 返回,绕过 Agent 的 length 守卫静默落日志。
- **非流式**:输出达到 `max_output_tokens` 时 `status === 'incomplete'`,802 行把它原样塞进 `finishReason`,Agent 不认识、按正常结束处理。

**修复**:与 OpenAIProvider 对齐——终止信号缺失即抛 `retriable: true`;或至少用 `usage.output_tokens >= maxTokens` 作截断证据降级为 `'length'`;`status === 'incomplete'` 映射 `'length'`。

### 7.4 🟠 上下文溢出检测正则漏掉 Anthropic 真实文案

**位置**:`agent/Agent.ts:415-423`

`isProviderContextOverflowError` 覆盖 `context_length_exceeded|request_too_large|maximum context|context window|超出.*上下文|上下文.*超`,但 Anthropic 超限的实际报错是 `prompt is too long: N tokens > M maximum`,全部不匹配。Claude 路线超限时不走 emergency-compact 恢复,直接把裸错误抛给用户。

**修复**:正则加入 `prompt is too long` / `too long.*maximum` 签名,或按 `status === 400 + 输入 token 接近上限` 辅助判定。

### 7.5 🟠 关键路径零测试:`pruneOldToolResults` 与 editor 包

**位置**:`core/src/tool/pruneToolResults.ts`(全仓库无对应测试)、`packages/@codepapr/editor/`

### 7.6 🟠 OpenAIProvider 工具定义 payload 非标准(双重嵌套)

**位置**:`providers/OpenAIProvider.ts:460-471`

每个工具同时写了顶层 `name/description/parameters` **和** `function: { name, description, parameters }`。OpenAI 规范是 `{ type: 'function', function: { name, description, parameters } }`;顶层字段多余且非标准。官方端点会忽略多余字段,但严格的兼容中转/网关可能 400;且 `sortedStringify` 会把双份字段全部序列化,浪费请求体。

### 7.8 系统性观察

四家 provider 大段复制粘贴了流解析循环却没有同步演进——同一套防御逻辑(流内 error 分类、截断归一化、提前结束判定)在 OpenAI/DeepSeek/Claude/Responses 四条路线上各缺一块:DeepSeek 缺 error 分类(唯一 🔴,可造成永久卡死),Claude 缺截断映射,Responses 两处都缺。

**建议**:把流终止判定、finish_reason 归一化、错误分类抽成共享层(类似 `streaming.ts` 已有的做法),并为"截断必须触发续写"补一条跨四家 provider 的契约测试。
