ONE REQUEST · TOP TO BOTTOM

How context is stacked, where memory lives

The model does not get one blob. Earlier bytes stay still so prefix cache works. Each memory kind enters one layer: short instructions every session, procedures this turn if useful, web citations only when searched.

What one request looks like

Read top to bottom. The top barely moves; the bottom grows. Color is how often it changes, not how important it is.

System core

System prompt, tool schemas, model params, AGENTS.md

Frozen for the session

Memory: compact or new session

New every user turn

Append-only at the tail

What each layer owns

Five slots, four clocks. A given fact belongs in one layer. The checkpoint is this task’s progress, not cross-session project memory.

STABLE PREFIX

Stable prefix · 01 + 02

  • Holds: identity and tool boundary, AGENTS.md, skill names + one-liners, short every-session memory, your long-term guidance.
  • Changes when: you edit rules, skills, or params. Newly saved memories do not rebuild the current prefix; they wait for compaction or the next session.
  • Budget: the memory slice is at most 24 items / 1500 tokens. Full skill files load via skill_load, not the prefix.
SESSION STATE

Session state · 03

  • Holds: the checkpoint after compaction (goal, todos, confirmed facts) and recent turns not yet folded in.
  • Changes when: round or length limits hit, or you run /compact. One intentional miss in exchange for a bounded window.
  • Does not hold: todos copied into project memory. Checkpoints die with the task; memory lives across sessions.
TURN RECALL

Turn recall · 04

  • Holds: retrieved old experience for this turn, mostly procedures. About 5 items / 1200 tokens.
  • Changes when: every user turn runs retrieval once. It exists only in this request — not in chat history.
  • Does not hold: web / MCP citations. Those are never auto-recalled, so outside text cannot become standing orders.
ACTIVE TAIL

Active context · 05

  • Holds: the current user message and this turn’s tool calls and results. Large dumps go to disk; reread with read_artifact.
  • Changes when: each turn appends at the tail. That is the only cache miss that is supposed to happen.
  • Does not hold: date, timezone, and diagnostics in the prefix — those would bust the cache every minute.

How a memory travels

The SQLite ledger is authoritative. The memory panel is the only place a human browses, edits, or forgets. There is no standalone memory file.

1 · Source

Who proposed it

You said remember / must / don’t, a test passed, cold-start summary, Agent memory_write, or a handwritten panel note.

2 · Gate

Keep or drop

A deterministic rule decides immediately: ordinary facts stay; injection, secrets, and dangerous commands are dropped. No “please click admit”.

3 · Ledger

Visible in the panel

Kept rows enter memory_entries. Same content replaces the old row. The current-session prefix still does not change.

4 · Destination

Layer by kind

Short instructions wait for compact or the next session; procedures can recall next turn; web citations appear only in search.

Every session

Into 02 session bootstrap

Handwritten notes, preferences, constraints, facts, conventions, verifications, decisions. At most 24 items / 1500 tokens.

Panel group: every session
On demand

Into 04 turn recall

Procedures. After save, the next user turn can retrieve them. They never sit in the every-session prefix.

Panel group: on-demand
Search only

Not auto-injected

Web / MCP citations. The model sees them only via memory_search. Never in 02, never auto-recalled.

Panel group: search only

AGENTS.md is the project rules you wrote — editing it rebuilds the prefix. Project memory is accumulated facts and preferences — a new write does not bust the current prefix. The checkpoint is where this task is. Do not copy one into another.

Three clocks

After a memory hits the ledger, when the model actually sees it depends on which beat you are on.

This turn

Ledger and panel update immediately. The current prefix does not. A procedure waits until the next user turn before it can be recalled.

Compaction

The checkpoint is rewritten (task progress). Project memory is re-rendered from the ledger, so short instructions finally enter the stable prefix.

New session

Session bootstrap always re-renders from the ledger. If it is still empty and a project graph exists, a structure / stack summary is written in the background and enters the prefix next time or after compact.
